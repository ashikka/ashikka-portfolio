Building a benchmark for product image search

How well do frontier models actually search a clothing catalogue?

I read the SID-1 post from turbopuffer a little while ago. They trained a search model with reinforcement learning and it beats GPT-5 at retrieval while being far faster and far cheaper. We had also started using it at work around the same time, and it was noticeably good. I wanted to try building something like that myself.

I found it interesting and wanted to explore a similar problem space. Most work like this has been on text search and I was curious what the same ideas look like when search is mostly visual. A product catalogue is a natural test case: the photo carries most of the information and the text carries very little. The description says "trousers in a cotton blend". The photo tells you the cut, the drape, the exact shade and whether the pleats are sharp or soft.

In this post I run the baseline evaluation: build the benchmark, put frontier and open-weight models through it, and see where one-shot retrieval falls short of agentic search. Fine-tuning comes later.

TL;DR

I used a catalogue of 3,081 Zara and H&M products from two Kaggle datasets, generated 96 search queries from the product photos. Then I built a simple harness that gives a model four search tools over the catalogue (keyword_search, semantic_search over a text embedding, and a product image embedding you can search with text via image_text_search or with a photo via similar_images) and ran the evaluation.

  • Claude Opus 5 leads overall at 0.906 nDCG, followed by Gemini 3.6 Flash at 0.885. Under one-shot retrieval, the best of the same indexes scores 0.473. Most of the gap to 0.906 comes from letting the model issue multiple searches.
  • keyword_search was the most used tool across models, but image_text_search was the strongest standalone retriever (0.473 vs 0.382 for BM25). Opus put about 30% of its calls there; smaller models stayed mostly on keywords.
  • Qwen3.5-9B beat Opus on precision (0.918 vs 0.833) but lost on recall, returning about 7 items per query against about 19 for Opus.
  • Opus costs about 56¢ per query, roughly 60x Qwen3.5-9B at about a penny, and is still the strongest system. The smaller model still beats every one-shot retriever.

Task definition

Given a natural-language query such as "beige suit trousers not skinny", the system should return the products in the catalogue that satisfy the query.

Each test case is a query plus an answer key over the full catalogue. Products are graded on three tiers:

Relevance tiers
GradenDCG gainMeaning
golden3.0Matches every constraint the query stated.
partial1.0Same kind of garment, misses at least one stated constraint.
irrelevant0.0Wrong garment, or breaks something the query ruled out.

Unmentioned attributes do not count against a result. Multiple products can be golden for the same query.

Retrieval is built on a vision-language embedding model: images and text are mapped into a shared vector space so that a product photo and a natural-language description of it land near each other. The model used here is Marqo/marqo-fashionSigLIP: SigLIP trained by Google as a more efficient CLIP variant, then fine-tuned by Marqo on clothing product data. Because the model already has strong garment vocabulary, the interesting failures tend to be fine-grained (cut, fit, exclusions) rather than basic category mistakes.

Generating the queries

Queries were generated synthetically and backwards, following Chroma's Context-1 report: choose supporting evidence first, then write the question from it. Here the evidence is a product photo rather than a document, so the pipeline looks like this.

Each claim is paired with the visual evidence that supports it:

{ "claim": "not a skinny fit",
  "visual_evidence": "straight leg cut and relaxed fit" }

Claims without evidence are discarded before any catalogue grading runs. That keeps the expensive step, scoring every product against every query, limited to queries that are already grounded in a photo.

Grading the whole catalogue

Every product was graded against every query, 96 × 2,982 = 232,839 pairs. The point is to know, up front, which products are correct answers. If a system fails to return one of them, that shows up in the score. If you only mark the products it did return, a system that finds three good items and misses twenty others still looks perfect.

Most pairs are obviously irrelevant, so a cheap model screens the catalogue first and a stronger model grades only the survivors, using the photo rather than category metadata. I then went through the tasks myself and hand-corrected grades that looked wrong.

The harness

The harness is a standard agentic search loop over the catalogue, adapted from the SID-1 setup. On each turn the model may call one or more search or inspection tools, including in parallel. It finishes by calling submit_ranking once with an ordered list of product ids. Rollouts are bounded by the budgets below; when a budget is exhausted the model is not cut off mid-turn, but is given one final turn with a notice to submit the best ranking it can from evidence already retrieved.

Six tools
ToolWhat it does
keyword_search(query)BM25 over the product title and description.
semantic_search(query)Dense search over BGE-small embeddings of the product text.
image_text_search(query)The FashionSigLIP image index, searched with a sentence.
similar_images(product_id)The FashionSigLIP image index, searched with a photo.
inspect_products(ids)The full record for a few products, photos included.
submit_ranking(ids)Ends the run with an ordered list of product ids.

submit_ranking accepts up to 50 product ids. inspect_products can attach photographs for up to four products per call, and a rollout may view at most 12 photographs in total. Search calls return up to 50 hits.

Per-rollout budgets
BudgetValue

The search tools read from four indexes over the catalogue:

Four indexes over one catalogue
IndexModelWhat it holds
visual_index.faissMarqo FashionSigLIPThe product photo. Searchable by text or by another photo.
text_index.faissBGE-small-en-v1.5The title and description as a dense vector.
bm25_index.pklBM25Keyword matching over the same text.
catalogue.dbSQLiteThe product records themselves.

SQLite holds product records. Retrieval indexes store vectors or terms and return product ids, which are resolved through the database.

Scoring does not re-judge answers at runtime. Grades are frozen on disk before any model runs; a submitted ranking is scored by lookup against those labels.

Metrics

Three numbers, all computed over the first ten results, which is roughly the page a shopper sees.

  • Recall: the fraction of golden products the system returned, out of all the golden products in the catalogue.
  • Precision: the fraction of returned products that are actually relevant, meaning golden or partial.
  • nDCG: a ranking-aware score that rewards putting the best items at the top: a golden is worth three times a partial, and slot 1 counts more than slot 10. This is the headline number.

Results

One-pass retrieval

Before diving deep into agentic search, it is worth establishing how the one-pass retrieval methods behave in isolation. The three baselines are BM25 keyword search over product text, BGE-small (text, semantic) dense retrieval over the same text, and FashionSigLIP text-to-image search over product photographs. FashionSigLIP is the strongest of the three. Many of the queries turn on visual attributes that never appear in the title or description, so an index over photos has a structural advantage. Between the two text indexes, BGE-small outperforms BM25.

Claude Opus 5 is first at 0.906 nDCG, then Gemini 3.6 Flash at 0.885, then GPT-5.6 at 0.833. The open models sit in a band from 0.779 (Qwen3.7-plus) down to 0.689 (Qwen3.5-9B).

Precision goes the other way. Qwen3.5-9B and Inkling are the highest at 0.918 and 0.913; Opus is at 0.833. The smaller models return cleaner lists. The frontier models find more of the correct set.

Cost

Cost and quality do not line up. GPT-5.6 is the most expensive model in the run and ranks third on nDCG. Across every model, most of the spend is input tokens from product photos rather than generated text. Several open models recover most of Opus's score at a much lower price.

Query type

Broken out by query type, the gap between Opus and Qwen3.5-9B is largest on literal attributes and on constraints that have to be read from the photo. Those two categories are also most of the eval. On inferred attributes Opus is near ceiling. Negation does not drive the gap: Qwen3.5-9B matches GPT-5.6 there. The separation is less about which linguistic pattern is hard, and more about how completely each model covers the catalogue.

Qwen3.5-9B is more precise

Split the scores and Qwen3.5-9B leads on precision. What it submits tends to be correct; it does not pad the ranking with doubtful items. Opus wins on nDCG because it keeps going and recovers more of the golden set, not because it judges candidates better.

It stops while it is still winning

About 5.8 correct answers exist per query on average. Opus submits 18.5 and never under-returns. Qwen3.5-9B submits 6.6 and under-returns on 20 percent of queries. On queries where Qwen3.5-9B happened to submit a longer list, its recall jumped from 0.63 to 0.88 while precision barely moved, so the trade was available in its own runs.

Every model opens text queries with keyword_search and image queries with similar_images. How they use those tools differs. Gemini is the standout: 10.7 turns and 21.4 distinct search strings per query. Opus is quieter on the same harness, 6.1 turns and 13.9 distinct queries, and opens far fewer photos (4.7 against Gemini's 8.1). The other frontier models sit between those two styles: GPT-5.6 batches the most calls per turn, while the smaller models take more turns but issue them serially. The implication is that high nDCG does not require Gemini's volume of search. Opus gets to the top of the table with fewer reformulations and less image inspection, so much of Gemini's extra tool use is exploration cost rather than necessary work.

Opus does not open most of what it ranks

Opus opens 4.7 photos per query and submits 18.5 items. It visually checks about a quarter of what it returns. The smaller models stay at or above one photo per submitted item; Inkling opens more photos than it finally ranks. Checking everything looks careful. Under this rubric it mainly protects precision and leaves recall on the table. The stronger policy is to spend the image budget on the head of the list and trust the retriever for the tail.

Future directions

Task diversity

The queries here are multi-constraint and depth-oriented, with at least one known answer in the catalogue. That is a useful stress test for tool use. It is not how most people shop. Real queries are shorter, leave constraints implicit, and often ask for a set rather than a single needle: every cream trench in a size range, or alternatives when the obvious match is out of stock. Outfit-level requests (a jacket that works with these trousers) and abstention (nothing in the catalogue fits) are also absent. Widening the task mix in those directions would change what "good policy" looks like, especially around when to stop.

Training

On this harness the gap between Qwen3.5-9B and Opus is concentrated in recall and stopping. Precision is already fine. A natural training path is to weight recall hard at the start of RL so the model learns to keep searching and to submit longer lists, then tighten precision once under-returning is no longer the failure mode.

Indexes and cost

The agent and the indexes were trained independently. The model learns to query a fixed BM25, BGE, and FashionSigLIP stack. Jointly adapting the visual index to the queries the agent actually issues, or adding cheap metadata filters for size and availability before photo inspection, would change both quality and the photo bill. Separately, nothing in this run sits where a production search box needs to sit on cost and latency.

Conclusion

We presented a small agentic product image search evaluation over a catalogue of Zara and H&M products: 96 synthetic queries, offline relevance labels, shared retrieval indexes, and eight models on the same tool harness. Under identical tools and labels, Claude Opus 5 leads Qwen3.5-9B by 0.22 nDCG.

Qwen3.5-9B is already as precise as Opus, and often more so. The items it returns are usually correct. It still trails on recall: it stops after a short list, while Opus keeps searching and recovers more of the good answers in the catalogue. Opus also opens fewer product photos and leaves more of the ranking to the retriever; the smaller models mostly inspect what they are about to submit.
